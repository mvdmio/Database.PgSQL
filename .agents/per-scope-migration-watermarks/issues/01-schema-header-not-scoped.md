# Bug: `db pull`'s per-scope migration header is not scoped to the exported schemas, causing schema-first bootstrap to silently skip an entire scope's migrations

Status: ready-for-human
Category: bug
Reported: 2026-07-11 (bug report generated during `mvdmio-suite` Compliance integration-test debugging, against v0.29.0)

> *This was generated by AI during triage.*

## Summary

`SchemaExtractor.GetCurrentMigrationVersionAsync` (and therefore `db pull`'s generated `schema.*.sql` header) always reports the migration watermark for **every scope that has ever executed against the target database**, ignoring the `schemas`/`_includedSchemas` filter that scopes every other part of the export. When a consumer feeds a schema file with this unscoped header into `DatabaseMigrator`'s schema-first bootstrap (`ApplySchemaAsync`) alongside another assembly that has **no embedded schema file of its own**, the migrator records a baseline row for that other assembly's scope anyway — from a header line whose corresponding table-creation SQL was never actually applied (it lives in a different app's schema file, scoped out of this one). The consumer then believes that scope is fully migrated and **silently skips every one of its migrations**. No error, no warning — the scope's schema/tables simply never get created.

This exactly reproduces in `mvdmio-suite`'s Compliance app integration tests today: every `compliance.*` table is missing, and every DB-touching test fails with `relation "compliance.people" does not exist` (or similar), even though 48 real, correct migrations exist for that scope and would create the tables fine if actually run.

## Why this matters relative to the feature's own intent

This is not the accepted limitation documented for per-scope watermarks. `docs/adr/0002-per-scope-migration-watermarks.md` and `.agents/per-scope-migration-watermarks/PRD.md` explicitly call out and *support* this exact shape of scenario:

> "schema-first works for the first scope to touch a fresh database, **or for multiple assemblies bootstrapped by a single `DatabaseMigrator` instance** (the integration-test scenario)." — ADR-0002, "Consequences" / considered-options section

> User story 10: "As a developer running integration tests, I want an empty database with multiple schema-first assemblies bootstrapped by a single migrator instance to apply every assembly's embedded schema and record a baseline per scope, **so that each scope's post-baseline migrations run correctly**."
>
> User story 11: "As a developer, I want each applied embedded schema to record a baseline row for its own scope, so that migrations folded into **one assembly's schema** are not re-run while another assembly still bootstraps." — PRD.md

The documented *unsupported* case is a **second, separate** `DatabaseMigrator` instance bootstrapping against an already-populated database (PRD "Out of Scope", ADR "Considered options" #4). Our case is a **single** `DatabaseMigrator` instance given three assemblies (`Auth.Db`, `Asp`, `Compliance.Db`) against one fresh, empty database — precisely the case the PRD says should work. It doesn't, because of the header-scoping gap below.

## Root cause

### 1. The header generator ignores the schema filter it already has

`src/mvdmio.Database.PgSQL/Connectors/Schema/SchemaExtractor.cs`:

- The class already carries `_includedSchemas` (lines 20-43) specifically to scope every other extraction method (tables, enums, sequences, etc.) to the schemas requested for this export.
- `GetCurrentMigrationVersionAsync` (lines 61-103) is the **one** extraction method that never consults `_includedSchemas`. It runs:
  ```sql
  SELECT DISTINCT ON (scope)
     identifier, name, executed_at, scope
  FROM "mvdmio"."migrations"
  ORDER BY scope, identifier DESC
  ```
  unconditionally — every scope that has ever run against this physical database, regardless of which schemas were requested for this particular pull.
- `GenerateSchemaScriptAsync` (lines 255-299) writes one `-- Migration version: <id> (<name>) [<scope>]` line per row this returns (lines 263-276), so **every** generated `schema.*.sql` file's header lists **every app's** latest migration, not just the exporting app's own.

This is fully reproducible today: in `mvdmio-suite`, every single app's `Schemas/schema.production.sql` (Auth, Commonplace, HealthCheck, Statistics, TranslationTools — all pulled from the same shared production Postgres instance) carries the **identical** 8-line header naming all seven scopes (`mvdmio.ASP`, `mvdmio.ASP.Jobs`, `mvdmio.Auth.Db`, `mvdmio.Commonplace.Db`, `mvdmio.Compliance.Db`, `mvdmio.HealthCheck.Db`, `mvdmio.TranslationTools.Db`), even though each of those apps' `.mvdmio-migrations.yml` restricts the exported **body** to only that app's own schemas (e.g. Auth's `schemas: [shared, public, auth]` produces a body with only `auth.*`/`shared.*` tables, but the same global 8-scope header).

### 2. The consumer trusts every header line unconditionally, from any contributing file

`src/mvdmio.Database.PgSQL/Migrations/DatabaseMigrator.cs`:

- `ApplySchemaAsync` (lines 352-400) reads every embedded `schema.*.sql` found across **all** assemblies passed to the migrator (`EmbeddedSchemaDiscovery.ReadAllSchemaContentsAsync`, line 354), applies each file's SQL body, then parses **every** file's header (`SchemaFileParser.ParseMigrationVersion`, line 375) and unions all the resulting `(scope, identifier)` pairs.
- Lines 378-393: it then records **one baseline row per scope — the highest identifier for that scope across all applied schema headers** — with no check that the assembly owning that scope actually contributed a schema file (or that the scope's tables were part of any applied body). A header line from `Auth.Db`'s `schema.production.sql` claiming `[mvdmio.Compliance.Db]` is at migration `202607101400` is treated exactly the same as if `Compliance.Db`'s own schema had been applied.

### 3. Concrete failure sequence (reproduced against `mvdmio-suite`)

`Compliance/test/mvdmio.Compliance.Tests.Integration/xUnit/Fixtures/DatabaseFixture.cs`:
```csharp
var dbMigrator = new DatabaseMigrator(DatabaseConnection,
   typeof(AuthDbAssemblyHook).Assembly, typeof(AspDbAssemblyHook).Assembly, typeof(ComplianceDbAssemblyHook).Assembly);
await dbMigrator.MigrateDatabaseToLatestAsync();
```

Against a fresh Testcontainers Postgres:

1. `ShouldApplySchemaAsync` (DatabaseMigrator.cs:319-344) finds the DB empty and finds embedded schema resources in `Auth.Db` and `Asp` (each has its own `Schemas/schema.production.sql`). `Compliance.Db` has **no `Schemas/` directory at all** — it has never been `db pull`-ed.
2. `ApplySchemaAsync` applies Auth's and Asp's schema bodies (creating only `auth`/`shared`/`asp`-owned tables), then parses both files' headers and records baseline rows for **every** scope named in either header — including `mvdmio.Compliance.Db @ 202607101400`, taken from Auth's header line, even though no Compliance table was ever created.
3. `PendingMigrationSelector` compares the 48 real, discovered `Compliance.Db` migrations (identifiers up to `202607101400`) against this fabricated baseline and finds none pending — every one is `<=` the "already applied" watermark. **Zero Compliance migrations run.**
4. Result: the test database has schemas `auth, information_schema, mvdmio, pg_catalog, pg_toast, public, shared` — no `compliance` or `isms` schema at all — and `mvdmio.migrations` contains a single ghost row: `202607101400 AddObjectivesAndKpis scope=mvdmio.Compliance.Db`, with no matching table ever created. Every Compliance DB-touching integration test fails with e.g.:
   ```
   Npgsql.PostgresException: 42P01: relation "compliance.people" does not exist
   ```

(Verified by temporarily adding a diagnostic xUnit test to the Compliance integration suite that dumps `information_schema.schemata`, `information_schema.tables`, and `mvdmio.migrations` after fixture init, then removing it — this write-up reflects that actual output, not a hypothetical.)

## Blast radius

- **Confirmed broken today:** any `DatabaseMigrator` instance that combines an assembly with real, undischarged migrations but **no embedded schema file** alongside another assembly that *does* have a schema file whose header happens to name the first assembly's scope. Compliance is the only current instance of this in `mvdmio-suite` (it has migrations but has never had a `Schemas/schema.*.sql` generated), but the mechanism is generic — it will silently reproduce for any future app added to a shared multi-assembly `DatabaseMigrator` before its own `db pull` has ever been run, or any app whose schema file is deleted/stale relative to its migrations.
- **Latent, not yet observed:** because every app's schema file carries the same global 8-scope header, any scope's migrations could be silently short-circuited the same way if that scope's own schema file goes missing or falls out of sync, even for apps that currently "work" only because their own file happens to independently agree with the foreign header lines.
- This is a `db pull`/schema-export defect, not an `mvdmio-suite` migration-authoring mistake — the Compliance migrations themselves are correct and would produce the right schema if actually run.

## Suggested fix directions (not prescriptive — flagging for design judgment)

Note: the exporter has no way to know, purely from Postgres system catalogs, which scope "owns" which physical schema — `Scope` is an application-side concept (`IDbMigration.Scope` defaults to `GetType().Assembly.GetName().Name`, per `src/mvdmio.Database.PgSQL/Migrations/Interfaces/IDbMigration.cs:37`) that never reaches the live database. Any fix has to work within that constraint. Two directions seem viable:

1. **Producer-side, explicit ownership.** Let each app declare which scope(s) it owns in `.mvdmio-migrations.yml` (alongside the existing `schemas:` list), thread that through `db pull` → `SchemaExportService` → `SchemaExtractor`, and filter `GetCurrentMigrationVersionAsync` to just the owned scope(s) (always including the owned scope's row even if `(none)`, to preserve self-consistency for schema-first bootstrap of that app alone). This removes cross-app ghost lines at the source and keeps every existing consumer behavior for the "own scope" case unchanged.
2. **Consumer-side, provenance-aware trust.** In `ApplySchemaAsync`, only record a baseline row for a scope if a schema file *whose own header also lines up with an applied body* vouches for it — e.g., don't let one assembly's header assert a baseline for a scope that contributed zero bytes of schema body across the whole operation. This is more defensive (protects against any future exporter carrying stale/foreign lines) but doesn't fix the exported files themselves, which remain misleading artifacts on disk.

These aren't mutually exclusive; (1) is the more complete fix (the exported file becomes honest), (2) is a good belt-and-suspenders safety net regardless.

## Agent Brief

**Category:** bug
**Summary:** Fix both sides of the unscoped-schema-header defect: `db pull` must stop emitting migration-watermark header lines for scopes the exporting app does not own, and `DatabaseMigrator`'s schema-first bootstrap must stop recording baseline rows for scopes that no applied schema file legitimately vouches for. Maintainer decision (2026-07-11): implement **both** the producer-side and consumer-side fixes in one change.

**Current behavior:**
- `SchemaExtractor.GetCurrentMigrationVersionAsync` returns the highest executed migration identifier for *every* scope in the migrations table, ignoring the extractor's included-schemas filter. The generated schema script header therefore names every scope that ever ran against the physical database, even when the export body is filtered to one app's schemas. On a shared database, every app's pulled `schema.*.sql` carries identical multi-scope headers.
- `DatabaseMigrator`'s schema-first bootstrap parses the headers of all applied embedded schema files, unions the `(scope, identifier)` pairs, and records one baseline row per scope with no provenance check. A header line naming a scope whose assembly contributed no schema file still produces a baseline, so that scope's real migrations are all at-or-below the fabricated watermark and are silently skipped. Confirmed end-to-end in `mvdmio-suite` (Compliance: 48 migrations skipped, no tables created, no warning).

**Desired behavior:**

*Producer side (`db pull` / schema export):*
- An app can declare which migration scope(s) it owns in `.mvdmio-migrations.yml`, alongside the existing `schemas:` list (prior art: `ToolConfiguration.Schemas`). Scope names match `IDbMigration.Scope` values (default: the migrations assembly's simple name).
- When scope ownership is declared, the generated schema header contains watermark lines only for the owned scope(s). If an owned scope has no executed migrations, the header degrades exactly as an empty database does today (the `(none)` form), so a schema-first bootstrap of that app alone stays self-consistent.
- Legacy scope-less migration rows (NULL scope, not yet backfilled) keep their current header representation regardless of the filter — they cannot be attributed to a scope at export time, and the existing consumer backfill heals them.
- When no ownership is declared, current behavior (all scopes) is preserved — existing consumers see no change until they opt in. The tool's README documents the new key and recommends declaring ownership for shared databases.

*Consumer side (`DatabaseMigrator` schema-first bootstrap):*
- An applied schema file may only establish baseline rows for scopes its own assembly vouches for: the scopes of migrations discovered from that assembly, plus that assembly's simple name (the default scope). Header lines naming any other scope are ignored for baseline recording, and a warning naming the file/assembly and the ignored scope is logged via the migrator's existing `ILoggerFactory`-based logger.
- Legacy scope-less header lines keep their current behavior (scope-less baseline healed by the backfill).
- Accepted limitation (document in the ADR): an assembly that has folded *all* migrations into its schema *and* overrides `IDbMigration.Scope` to something other than its assembly simple name cannot be vouched for; its baseline is rejected with the warning. Later migrations in that scope then fail loudly (objects already exist) instead of being silently skipped — loud failure is the intended trade-off.
- Net effect for the reported scenario: a single migrator given several assemblies where one has migrations but no embedded schema file must run that assembly's migrations from zero, even when another assembly's schema header names its scope.

**Key interfaces:**
- `ToolConfiguration` (and its loader/`db init` template) — new optional scope-ownership list, normalized like `Schemas`.
- The pull pipeline (`PullHandler` → `SchemaExportService` → `SchemaExtractor`) — thread the owned scopes through to header generation; `SchemaExtractor` gains the owned-scopes input alongside its existing included-schemas input.
- `SchemaExtractor.GetCurrentMigrationVersionAsync` — filters returned rows to owned scopes when provided (public API: additive only, no breaking signature change).
- `DatabaseMigrator`'s schema-apply step — provenance check per applied schema file; needs the per-file assembly association that `EmbeddedSchemaDiscovery` already returns.
- `docs/adr/` — record the scope-ownership model and the vouching rule (new ADR or an amendment to ADR-0002), including the accepted limitation above.

**Acceptance criteria:**
- [ ] Exporting with declared scope ownership from a database whose migrations table contains foreign scopes yields a header naming only the owned scope(s); the reporter's shape (two scopes in two schemas, export filtered to one) produces no foreign-scope line. (Reproduction exists: see triage verification comment above.)
- [ ] Exporting with no declared ownership produces today's header unchanged.
- [ ] An owned scope with zero executed migrations exports the `(none)` header form.
- [ ] Schema-first bootstrap with two assemblies — only one contributing a schema file whose header (deliberately) also names the other assembly's scope — runs all of the other assembly's migrations and records no ghost baseline for it, and logs a warning about the ignored header line.
- [ ] Existing multi-assembly bootstrap behavior is unchanged when every schema file's header names only its own assembly's scope(s) (existing `SchemaFirstMigrationTests` suite stays green, including the legacy scope-less header test).
- [ ] Unit tests cover the extractor's owned-scope filtering and the consumer's vouching rule per the regression-coverage section above; integration tests extend the existing schema-first suite with the cross-scope ghost-header fixture.
- [ ] README(s) document the new config key and the consumer-side provenance rule; ADR added/amended; `<PgSqlVersion>` bumped MINOR (backward-compatible feature + bug fix; no breaking API change).
- [ ] `dotnet format` → `dotnet build` → `dotnet test` all pass, run sequentially.

**Out of scope:**
- The per-scope empty-database check (second, separate schema-first migrator against a populated database) — already a tracked follow-up in the PRD, unchanged by this fix.
- Deriving scope↔schema ownership automatically from the database — impossible from system catalogs; ownership is declared configuration by design.
- Removing the legacy scope-less header/backfill path — reserved for the next major version per ADR-0002.
- Any change to `mvdmio-suite` itself (regenerating its schema files with ownership declared is consumer follow-up work outside this repo).

**Implementation — 2026-07-11 (agent)**

Implemented both fixes in one change, released as 0.30.0 (MINOR):

- *Producer:* `ToolConfiguration` gains an optional `scopes` list (normalized like `schemas`, threaded through `db pull` and `db cleanup` via `SchemaExportService` → `SchemaExtractor`). `SchemaExtractor` gains an additive constructor overload + `OwnedScopes` property; `GetCurrentMigrationVersionAsync` filters to `scope IS NULL OR scope = ANY(ownedScopes)` when ownership is declared. No ownership declared → header unchanged; owned scope with zero rows → `(none)` form; legacy scope-less rows always keep their line.
- *Consumer:* new pure module `SchemaBaselineSelector` — an applied schema file only establishes baselines for scopes its assembly vouches for (scopes of migrations discovered from that assembly + the assembly simple name). `DatabaseMigrator.ApplySchemaAsync` logs a warning per ignored foreign header line (naming file, assembly, scope, identifier) and records no ghost baseline.
- *Tests:* 7 unit tests for the vouching rule (`SchemaBaselineSelectorTests`); 5 extractor integration tests incl. the reporter's shape (schemas + scopes filtered together); end-to-end ghost-header integration test (`SchemaFirstMigrationTests`, new `schema.ghostheader.sql` fixture) proving the foreign-scope assembly's migrations run from zero with a logged warning. Full suite green: 288 tests, 0 failures.
- *Docs:* ADR-0003 (scope ownership + vouching rule + accepted loud-failure limitation), all three READMEs, CONTEXT.md glossary ("Owned scope", "Vouched scope").

Ready for human review.
