# Changelog

## 2026-11-18: The db tool exits non-zero on every error and stops on Ctrl+C
Every `db` command now ends with exit code `0` (it finished, including when it had nothing to do), `1` (it could not do what was asked), or `130` (you pressed Ctrl+C). Before, a missing connection string, an unknown `--environment`, a missing `.mvdmio-migrations.yml`, `db init` over an existing file, `db migrate to` with an identifier no migration reaches, a failed schema export in `db pull` or `db cleanup`, and a `db copy` with the same source and destination or mismatched schemas printed an error and still exited `0`, so a pipeline carried on as if the command had worked. A script that relied on that `0` now sees `1`; the messages are unchanged. Ctrl+C now stops the tool the same way in every command. During the build it kills the `dotnet build` process tree, prints `Cancelled.`, and exits `130`. During `db migrate` the running migration finishes and records itself (an embedded schema that is being applied finishes too), no further migration runs, and the tool prints `Cancelled.` and exits `130`; while it waits for another instance's migration lock it stops at once. `db pull`, `db copy`, and `db cleanup` cancel the database call in progress. A second Ctrl+C exits at once with `130`, and PostgreSQL rolls back the open migration transaction. In the library, a cancelled `MigrateDatabaseToLatestAsync`, `MigrateDatabaseToAsync`, or `DatabaseMigrator.RunAsync` lets the running migration finish and record its row, starts no further migration, and throws `OperationCanceledException`, not a `MigrationException`. Version 0.44.1, which has no entry of its own, made the tool build the migrations project with .NET build servers off, so `db migrate` and `db cleanup` no longer hang after a successful build.

## 2026-11-18: Targets net10.0 and net11.0, drops net8.0 and net9.0
The library and the `db` tool now target `net10.0` and `net11.0`, version 0.44.0. `net8.0` and `net9.0` are no longer supported, so a project on either framework cannot update past 0.43.0. Building against the package now needs the .NET 10.0.100 SDK or newer.

## 2026-11-17: A migration can run outside a transaction
A migration can now override `IDbMigration.RunsInTransaction` to return `false`, so a change to a large table no longer holds its locks for the whole migration. Before, the migrator ran every migration in one transaction: the first `ALTER TABLE` kept its lock through the back-fill and the index build, writes from the running app waited for all of it, and `CREATE INDEX CONCURRENTLY` failed with "cannot run inside a transaction block". Now such a migration runs with no transaction, each statement commits at once, and the migrator records the migration only after the whole of it finishes. If it fails partway, the earlier statements stay applied, the migration stays unrecorded, and the next migrate runs it again from the start, so it must be safe to re-run from any point. The member defaults to `true`, so existing migrations run as before.

## 2026-10-29: The db tool loads a migrations project on a newer version of one of its own packages
A migrations project that references a newer version of a package the tool also ships, such as Npgsql 10.0.3, now loads. Before, the command stopped with `FileLoadException: The located assembly's manifest definition does not match the assembly reference`. The project now gets the tool's copy of that package.

## 2026-10-28: The db tool loads a migrations project that uses NuGet packages
`db cleanup`, `db migrate`, and every other command that loads the migrations project now find that project's NuGet package assemblies. Before, a migrations project with a type that names a package type, such as a class that derives from one, stopped the command with `ReflectionTypeLoadException: Could not load file or assembly`. A class library's build output holds no package assemblies, so the tool now reads them from the project's `.deps.json` and the package folders that restore recorded. An assembly the project does not list still stops the command, so cleanup never deletes the file of a migration it could not load.

## 2026-10-25: An awaited query that includes a collection throws QueryException
An awaited query on the Query surface that includes a collection (`Include`, with or without `ThenInclude`, `Skip` or `Take`) now throws `QueryException` with the Postgres error and the SQL when the database rejects it. Before, it threw a `NullReferenceException` that hid the error. The fix is the `linq2db` upgrade from 6.3.0 to 6.5.1.

## 2026-10-24: A cancelled call throws OperationCanceledException
A cancelled async call on `DatabaseConnection` (`Dapper.ExecuteAsync`, `QueryAsync`, and the other Dapper calls) now throws `OperationCanceledException` instead of a `QueryException` that wrapped it. `catch (OperationCanceledException) when (ct.IsCancellationRequested)` now works for Dapper calls as it already did for LINQ calls. A SQL error, a timeout, or a lost connection still throws `QueryException` with the SQL attached.

## 2026-10-17: InTransaction now reports the original failure
When the database connection breaks inside `InTransaction`, `InTransactionAsync`, or `InTransactionAsync<T>`, the call now throws the exception your action saw. Before, the failed rollback hid it behind an `ObjectDisposedException`. The `DatabaseConnection` also stays usable afterwards: `RollbackTransaction` and `RollbackTransactionAsync` now always clear the transaction, so the next query or transaction starts on a fresh connection.

## 2026-10-09: Connection pools now capped and named
Every connection pool the library builds now holds at most 10 connections, down from 100, so that several programs can share one Postgres server without using up its connection limit. Each connection also shows the name of the program's entry assembly in `pg_stat_activity.application_name`. A program that needs more connections can add `Maximum Pool Size` to its connection string, or set the cap and the name once with `DatabaseConnectionFactorySettings` on the connection factory or in `AddDatabase`.

## 2026-10-07: Late-merged migrations now run
A migration merged from another branch now runs at the next migrate, even when a higher-numbered migration in the same scope already ran. Each one runs with a warning in the log and in `db migrate` output, and the first migrate after upgrading also runs any that were skipped before. `db cleanup` no longer deletes a migration file that any configured environment still has to run.
