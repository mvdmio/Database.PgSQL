# Admit composite primary keys, and register a composite relation with a predicate rather than a key API

A **Table definition** had to declare exactly one primary-key property. A consuming application could not declare a single one of its keyed tables: fifty-three of its fifty-nine have a two-column key, every one shaped `(account_id, <entity>_id)`, and the generator abandoned each table outright — no data type, no repository, no query mapping, no **Relations**. The whole **Query surface** the library exists to expose, and the OData front-end built over it, was unreachable for the application that asked for it. That composite key is the application's tenancy guarantee rather than an incidental shape: `account_id` is in every key and every foreign key, so no query can reach another tenant's row through a **Relation** by accident, and demoting it to a filtered column would trade a structural guarantee for a call-site convention.

We decided to admit two or more primary-key properties per Table definition, in source declaration order as the **Key order**; to let a **Relation property** name one foreign-key property per member of the target's key, paired positionally; to give every repository one fixed-named primary-key lookup and delete instead of per-property ones; and to refuse a nullable key member.

## Considered options

**How the key order is stated:**

- **Source declaration order (chosen).** The provider treats key order as cosmetic — it changes only the ordering of predicates in a generated `WHERE` clause, and key metadata is not consumed by the read path at all — so the only audience for an ordinal is the generated parameter order, which declaration order already gives.
- **An ordinal argument on the attribute.** Rejected: it buys nothing over the order the file already shows, at the cost of four malformed-ordinal cases to diagnose (missing, duplicated, non-contiguous, out of range).

**How a composite relation is declared:**

- **A variadic foreign-key-name parameter, paired positionally against the target's key (chosen).** A single-argument declaration keeps compiling unchanged, so nothing that already ships has to be revisited. Binary-breaking, source-compatible.
- **Naming the target's columns explicitly.** Rejected as unmotivated scope: the far end stays the target's primary key, nothing in the driving schema needs a relation to a non-primary unique key, and it would double what every declaration states.
- **Explicit pairing syntax.** Rejected: it restates the target's key order and buys no safety — with two same-typed columns a transposed pair is silently wrong under either scheme.

**How the composite association reaches the provider.** Three of the provider's forms carry composite keys, and all three were executed against PostgreSQL 18 in a prototype: they render identical SQL and all support eager loading at every level.

- **The predicate form (chosen)**, exposed as two new overloads on the public mapping builder, one per cardinality. Its equalities are compile-checked member by member, so a renamed property is a build error.
- **The comma-separated key-name form.** Rejected: it carries member *names* as strings. The prototype showed a wrong name registers without complaint and fails only at the first query, and that a mismatched key count throws on one entity while silently dropping the association from the other. The generator would emit names it had just validated, but the mapping builder is public API a consumer calls by hand.
- **The key-expression form with a composite key.** Rejected and actively guarded against. The provider's key type parameters are unconstrained, so an anonymous type compiles, registers as a *single* key literally named after its constructor, and fails only at the first query with a coercion error naming the two entity types. A generator test asserts that shape is never emitted.
- **Unifying the single-column path onto the predicate form.** Rejected: regression risk for relations that already ship, in exchange for nothing.

**How the primary-key lookup is named:**

- **One fixed name on every repository (chosen).** `GetByPrimaryKeyAsync` and `DeleteByPrimaryKeyAsync`, taking one parameter per key member in **Key order**. A reader never has to discover what the lookup is called for a given table.
- **A name derived from the key's properties.** Rejected: over a composite key it would have to concatenate them, and the reason to prefer a fixed name — that it is the same everywhere — evaporates if single-column tables keep a derived one. So this renames a method on every existing repository, which is the largest consumer-visible cost of this decision and is accepted: the package is pre-1.0 and the project's versioning rule makes a breaking change a minor bump.

## Consequences

- **A nullable key member is a build error, and that is load-bearing rather than tidy.** When the provider believes a key column is nullable on both sides of a join, its null-comparison mode — kept deliberately by [ADR 0004](0004-linq2db-as-the-queryable-provider.md) because it matches C# semantics — widens the join condition with an "or both are null" alternative. Measured against PostgreSQL 18 on two fifty-thousand-row tables with a matching two-column btree index on each side, that widening demotes the second column out of the index condition into a filter: index searches rise from 250 to 50,000, shared buffers from 1,516 to 25,116,417, and runtime 232x on a nested loop; on a hash join the second column becomes a join filter removing 24,975,000 rows, at 54x. Row counts are identical, so the widening is pure cost. Refusing a nullable key member removes the widened form wherever the key member's type makes null impossible — which is every key member except a reference-typed one, because the provider reads `string` as nullable whatever its C# annotation says. A `string` key member is therefore still widened until the mapping states its nullability, which [ADR 0007](0007-declared-column-nullability.md) makes it do. The converse was confirmed too: a nullable *foreign* key against a non-nullable key member renders plain equality.
- **A polymorphic junction needs nothing further from the library.** A per-kind stored generated column is an ordinary mapped column that happens to be database-computed, already expressible with the generated-column attribute, and a **Relation** against it is an ordinary **Relation** — including the nullable-foreign-key case above, since such a column is null for every other kind. A discriminator-aware relation form was considered and rejected as a large feature for something the database already expresses.
- **A foreign key need not be part of the declaring table's own primary key, nor a subset of it.** The driving case is a junction with a four-column key whose relation to another table is keyed on the tenancy column plus a generated column that is in no key at all.
- **Two diagnostics are added and five change scope.** `PGSQL0019` for a foreign-key arity that does not match the target's key, and `PGSQL0020` for a nullable key member. `PGSQL0004` is reworded from "exactly one" to "at least one"; `PGSQL0013` names the key position alongside both properties; `PGSQL0010` widens to cover a `[Unique]` property whose generated lookup would take the fixed primary-key name; `PGSQL0006` narrows to unique columns only; and `PGSQL0012` is now reported once per unresolved foreign-key name rather than once per relation, because a composite declaration can get more than one name wrong and each is a separate mistake. Key-level problems abandon the table, because a malformed key leaves every generated signature undefined; relation-level problems drop only the relation, per [ADR 0005](0005-table-relations-on-relation-properties.md).
- **`[Unique]` columns keep their per-property lookup and delete names**, because the property name is the only thing distinguishing two unique lookups on one table. The internal notion of "lookup properties" therefore stops meaning *primary key plus unique columns* and narrows to *unique columns*.
- **Each key member is emitted with the key flag on its column registration.** Key metadata is not required by the read path, but the prototype established that its absence makes a split eager load wrap the parent in a deduplicating derived query instead of joining the parent table directly, so emitting it is a free plan improvement.
- **The eager-loading path is untouched.** The include operators, their marker interface, the library's own include expression nodes and the execution-time translation are all unchanged, which is what preserves ADR 0005's already-tested guarantees across a composite relation: a query composed before a transaction opens still executes inside it, and exception translation, SQL diagnostics and the disposed-connection error still apply.
- **Nothing verifies a composite key or a generated column against the real schema.** Same trade the library already makes for column names and for relations generally: the table attribute has never emitted DDL and migrations stay hand-written.
- **The OData front-end needs no changes and gets its own conformance coverage.** A composite-key entity pair sits alongside the single-key one, and `$filter`, `$orderby`, `$top`, `$skip`, `$count`, `$select`, navigation-path filtering in both cardinalities, the stable-paging token and `$expand` to one, to many and two levels deep are all pinned over it. Two things are worth a consumer knowing: `$select` appends *every* key column rather than one, and server-driven paging becomes a lexicographic ladder across the key members.
- **API surface.** `[PrimaryKey]` is unchanged and now admits more than one property. `[Relation]`'s single foreign-key-name parameter becomes variadic and its single-name property a collection — binary-breaking, source-compatible. The mapping builder gains two predicate overloads; the key-based ones are untouched. Every repository's primary-key lookup and delete are renamed. MINOR bump under the project's pre-1.0 rule.
