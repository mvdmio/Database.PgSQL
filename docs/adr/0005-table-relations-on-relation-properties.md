# Declare table relations on a relation property and compose eager loading at execution time

A **Table definition** described one table in isolation, so the **Query surface** could not span tables and ADR 0004 recorded that as a deliberate deferral: the provider expresses joins perfectly well, but the generator had no **Relation** model to generate them from. We decided to introduce that model as a **Relation property** — a member on the Table definition typed as the *other* Table definition, annotated with the name of the foreign-key property that resolves it — and to expose it on the Query surface twice over: reaching through it in a predicate needs no new API at all, while materializing the related rows is an explicit, opt-in operator. That operator records its intent as the library's own expression nodes and is translated into provider calls at execution time rather than being forwarded to the provider when it is composed.

Two facts constrained the design before any preference could apply. A source generator analyses the pre-generation compilation and cannot see its own output, so a Relation property can only be typed as the other Table definition and never as that table's generated data type. And the far end of every Relation is always the target's declared primary key, so the foreign key is the only thing a declaration ever needs to state — one property per member of that key, which for a single-column key is one name and is what the provider's key-expression association overloads take. [ADR 0006](0006-composite-primary-keys.md) admits composite keys and registers those relations through the provider's predicate overload instead; the declaration model here is unchanged by it.

## Considered options

**How a relation is declared:**

- **An attribute on a relation property (chosen).** The property's type states the target and, by whether it is a collection, the cardinality; the attribute states only the foreign key. One attribute therefore covers both directions without a second name that could contradict the type. The cost is real and was accepted: property validation previously rejected every public property that was not a mappable column and had no opt-out, so the attribute had to become one.
- **An attribute on the foreign-key scalar property.** Rejected: it needs no change to property validation, which made it the cheaper option, but it gives the generated data type no navigable member to name in a predicate or an include, which is the entire point.
- **A class-level attribute naming both the target and the foreign key.** Rejected: needs `nameof` strings for something the type system could carry, and loses the compile-time tie between a declaration and the property it describes.
- **Convention over the column names.** Rejected: two relations at the same target — a created-by and an updated-by pointing at the same user table — cannot be resolved by any convention, and a wrongly inferred foreign key is a silently wrong join. This library already rejects lossy convention elsewhere by offering an explicit column-name attribute.

**How relations pair:**

- **One-directional, never paired (chosen).** Each declaration is self-sufficient, and the provider's association metadata is one-directional anyway, so pairing would add a matching rule and ambiguity diagnostics in exchange for nothing at translation time. A consequence worth stating plainly: a cycle is therefore the normal case, not an edge case, because a child-to-parent relation alongside a parent-to-children relation already is one.
- **Paired and validated.** Rejected: buys consistency checking for a mistake the per-side diagnostics already catch.
- **Declare one side, generate the other.** Rejected: it would put a member on a generated data type with no counterpart in the Table definition, contradicting the definition being the single source every generated type derives from.

**How eager loading composes:**

- **Record includes as the library's own expression nodes and translate them at execution time (chosen).** Forced, not stylistic — see below.
- **Forward to the provider's eager-loading operator when the include is composed.** Rejected on evidence. That operator ends by hard-casting the result of the source's own provider back to a provider-internal query type, which fails outright against this library's decorator; and the documented workaround — delegating the decorator's provider to the provider's own — would bind the query to a connection and transaction at composition time and drop the decorator from the chain entirely. That would break the already-tested guarantee that a query composed before a transaction begins still runs inside it, and would silently disable exception translation, SQL diagnostics and the disposed-connection error for everything composed after an include.
- **Materialize related rows eagerly and always.** Rejected: makes every query pay for data almost none of them want, and there is no way to opt out of a shape.
- **Lazy loading.** Rejected: the generated data types are plain classes with no proxying or change tracking, and a data access library that issues queries from a property getter after materialization is a category this one has deliberately stayed out of.

## Consequences

- **The Query surface is no longer single-table.** It stays read-only, and it spans tables only along a declared Relation. ADR 0004's consequence stating that cross-table querying is not unlocked is superseded by this decision; it is left in place, pointing here, because the record that single-table was reasoned rather than accidental is worth keeping.
- **Filtering and ordering across a relation cost no API at all.** A predicate reaching through a Relation property translates as soon as the relation is registered, and the provider's join optimisation collapses the outer join to an inner join when the predicate lands on the joined table. This is also why relations are always registered as nullable joins: it is the safe default, and it costs nothing in the filter case, whereas an inner join chosen by mistake silently drops rows.
- **The execution-time translation is what preserves every existing query guarantee**, and it also makes the library more permissive than the provider: the provider's own chaining marker does not survive intervening operators, so it requires the second level of an include chain to immediately follow the first. Emitting the pair contiguously at execution time removes that restriction for consumers.
- **A latent defect in the expression-tree rewriter is closed by this work rather than deferred again.** Every decorator constant was replaced with the one root the rewriter was handed, regardless of which query source it belonged to. That was unreachable while a meaningful two-table query could not be expressed; advertising cross-table querying makes a correlated subquery across two generated repositories an obvious thing to try, and it would have silently read the wrong table. Each constant now resolves against its own source, which makes that query work when the sources share a connection and an error when they cannot.
- **A to-many materialisation costs one additional statement per level**, and each detail statement re-runs the parent query as a derived table rather than passing a list of keys. This is the provider's split-query strategy and it is not configurable — the option that once controlled it was removed two majors before the version in use, and there is no replacement. One documented consequence follows: a filter on the main query also constrains a to-many detail query, because the detail query re-derives its parents from the main one. On a self-referencing hierarchy that surprises, and the answer is the filtered include overload rather than working around the provider.
- **The most damaging failure mode is outside this library and cannot be fixed from inside it.** With an OData front-end's null-propagation rewriting left at its default, an expanded collection comes back empty while the detail queries run and their rows are discarded — no exception, no warning. The default is selected by matching the query provider's namespace against a hardcoded allowlist this library's provider is not on. All that is available is documentation, placed where materialisation is introduced rather than only in the front-end section.
- **An invalid relation is reported without abandoning the table.** This departs from every existing hard error in the generator, which stops generating for the table. Abandoning it here would suppress the generated data type and cascade into a wall of type-not-found errors that buries the one message describing the actual mistake.
- **Relation targets must be Table definitions in the same compilation.** This keeps cross-table validation to a single path over models the generator pipeline already produces, rather than a second path over metadata symbols, and it has a useful side effect: every association and both of its endpoint mappings are always registered by one module initializer, which closes the provider's silent failure mode where an unregistered target falls back to a default table name and surfaces as a missing-relation error from PostgreSQL.
- **Nothing verifies a Relation against the real schema.** A Relation is a mapping claim about columns that already exist; the table attribute has never emitted DDL and migrations stay hand-written. A declaration naming the wrong foreign key type-checks, registers, and produces a wrong join at run time — the same trade this library already makes for column names.
- **Relations reach the Dapper surface not at all.** Its generated SQL is baked at generation time with flat column aliasing and a flat parameter dictionary, and joined reads there would be new machinery for no stated need. Repositories stay hybrid in exactly the way ADR 0004 described.
- **API surface.** Additive: a new attribute, mirrored relation properties on generated data types, include operators and a marker interface on the public extensions class, and overloads on the public mapping builder. The property-validation change only skips properties carrying an attribute no existing code can have. MINOR bump. (The attribute's single foreign-key-name parameter later became variadic — see ADR 0006.)
